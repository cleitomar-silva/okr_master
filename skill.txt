Sistema de Gestão de OKRs
1. Objetivo do sistema
Desenvolver um sistema web de gerenciamento de OKRs, organizado por empresa, com controle de acesso baseado em três níveis de permissão:

desenvolver o sistema com containers com react vite e laravel e mysql no banco de dados. porta do frontend 5176, do backend 9192 e o banco 3308

Administrador
Gestor
Colaborador

O sistema deverá permitir o gerenciamento hierárquico de:

Eixo → Objetivo → Ação → Iniciativa

Todos os dados de OKRs deverão pertencer à empresa atualmente selecionada pelo usuário.

2. Controle de acesso
2.1 Administrador
O usuário com nível Administrador possui acesso completo ao sistema.
Pode:

Acessar todas as páginas.
Cadastrar usuários.
Editar usuários.
Excluir usuários.
Cadastrar empresas.
Editar empresas.
Excluir empresas.
Cadastrar, editar e excluir Eixos.
Cadastrar, editar e excluir Objetivos.
Cadastrar, editar e excluir Ações.
Cadastrar, editar e excluir Iniciativas.
Vincular usuários às Ações.
Vincular usuários às Iniciativas.
Alterar a empresa selecionada.

O Administrador não deve ter nenhuma restrição de acesso baseada em empresa para as páginas administrativas.

2.2 Gestor
O usuário com nível Gestor pode gerenciar os dados das páginas às quais possui acesso.
Pode:

Acessar a tela inicial.
Visualizar OKRs da empresa selecionada.
Cadastrar Eixos.
Editar Eixos.
Cadastrar Objetivos.
Editar Objetivos.
Cadastrar Ações.
Editar Ações.
Cadastrar Iniciativas.
Editar Iniciativas.
Vincular usuários às Ações.
Vincular usuários às Iniciativas.
Alterar a empresa selecionada, desde que possua vínculo com ela.

Não pode:

Acessar a página de Usuários.
Acessar a página de Empresas.
Cadastrar ou excluir usuários.
Cadastrar ou excluir empresas.

Importante: o Gestor pode cadastrar e editar os itens de OKR, mas não pode excluir qualquer item

3. Colaborador

O usuário com nível Colaborador pode:

Acessar a tela inicial.
Visualizar os OKRs das empresas às quais está vinculado.
Cadastrar Eixos.
Cadastrar Objetivos.
Cadastrar Ações.
Cadastrar Iniciativas.
Marcar/desmarcar o check das Iniciativas às quais possui acesso.
Visualizar o progresso das Ações.

Não pode:

Acessar Usuários.
Acessar Empresas.
Editar itens existentes.
Excluir itens.
Cadastrar ou editar usuários.
Cadastrar ou editar empresas.

O Colaborador somente poderá cadastrar dados dentro das empresas às quais estiver vinculado.

4. Usuários

Criar uma página Usuários, disponível exclusivamente para Administradores.

Cadastro de usuário

O formulário deverá conter:

Nome
E-mail
Permissão
Colaborador
Gestor
Administrador
Empresas vinculadas
Senha

Um usuário poderá estar vinculado a uma ou várias empresas.

Regras
Usuários Administradores possuem acesso administrativo completo.
Usuários Gestores podem acessar somente as empresas às quais estão vinculados.
Usuários Colaboradores podem acessar somente as empresas às quais estão vinculados.
O cadastro de usuário não deve ser vinculado à empresa atualmente selecionada.
O Administrador poderá cadastrar um usuário e selecionar várias empresas para esse usuário.
O Administrador poderá posteriormente editar os vínculos de empresas do usuário.

5. Empresas

Criar uma página Empresas, disponível exclusivamente para Administradores.
Cadastro de empresa
Campos:
Nome da empresa
CNPJ
Cor
A cor cadastrada será utilizada como background da área central da barra superior, indicando visualmente a empresa atualmente selecionada.

O sistema deverá possuir uma barra de navegação superior fixa.

A barra deverá conter três áreas principais:

Esquerda

Menu de navegação do sistema.

Exemplo:

Início
Usuários
Empresas

As opções deverão aparecer de acordo com o nível de permissão do usuário.

Centro

Exibir o nome da empresa atualmente selecionada.

Exemplo:

Cafaz Saúde

O seletor deverá apresentar somente as empresas às quais o usuário possui acesso.


Direita

O dropdown poderá conter:

Nome do usuário
Meu perfil
Alterar senha

8. Regra fundamental de empresa

Essa é uma regra central do sistema:

Todo cadastro de Eixo, Objetivo, Ação e Iniciativa deverá obrigatoriamente estar vinculado à empresa atualmente selecionada.

Exemplo:

Se o usuário estiver em:

Cafaz Saúde

e cadastrar:

Eixo: Crescimento

esse Eixo deverá possuir internamente:

empresa_id = ID da Cafaz Saúde

Se o usuário trocar para:

Cafaz Corretora

o sistema deverá carregar somente os dados pertencentes à Cafaz Corretora.

8.1 Exceções

Essa regra não se aplica a:

Usuários

O cadastro de usuários é global.

Um usuário pode possuir vínculo com:

Cafaz Saúde
Cafaz Corretora
ambas
Empresas

O cadastro de empresas também é global.

Somente Administradores possuem acesso a essa funcionalidade.

Empresa
└── Eixo
    └── Objetivo
        └── Ação
            └── Iniciativa

Exemplo:

Cafaz Saúde
│
├── Crescimento
│   │
│   ├── Aumentar carteira de clientes
│   │   │
│   │   ├── Criar campanha comercial
│   │   │   ├── Definir público-alvo ✓
│   │   │   ├── Criar material ✓
│   │   │   └── Publicar campanha
│   │   │
│   │   └── Melhorar conversão
│   │       ├── Revisar processo
│   │       └── Treinar equipe
│   │
│   └── Expandir canais
│
└── Eficiência
    └── Reduzir custos


10. Tela Inicial

A página inicial deverá apresentar um card principal com o título:

Visão Geral de OKRs

O card deverá apresentar a estrutura hierárquica de:

Eixos
Objetivos
Ações
Iniciativas

A interface deverá deixar clara a relação entre os níveis.

11. Eixos

Um Eixo pertence diretamente a uma empresa.

O usuário deverá poder:

Cadastrar Eixo.
Visualizar Eixo.
Editar Eixo, conforme permissão.
Excluir Eixo, conforme permissão.

Campo:

Nome do Eixo

Um Eixo poderá possuir vários Objetivos.

12. Objetivos

Cada Objetivo deverá obrigatoriamente pertencer a um Eixo.

O usuário deverá poder:

Cadastrar Objetivo.
Visualizar Objetivo.
Editar Objetivo, conforme permissão.
Excluir Objetivo, conforme permissão.

Campo:

Nome do Objetivo

Um Objetivo poderá possuir várias Ações.

13. Ações

Cada Ação deverá obrigatoriamente pertencer a um Objetivo.

Campos:

Nome da Ação
Usuários responsáveis

Uma Ação poderá possuir um ou vários usuários vinculados.

Na listagem da Ação deverá aparecer:

Nome da Ação

e logo abaixo:

Barra de progresso

Exemplo:

Criar campanha comercial

██████████████░░░░░░ 70%

A porcentagem deverá ser calculada automaticamente com base no progresso das Iniciativas pertencentes à Ação.

14. Iniciativas

Cada Iniciativa deverá obrigatoriamente pertencer a uma Ação.

Campos:

Nome da Iniciativa
Usuários responsáveis

Uma Iniciativa poderá possuir um ou vários usuários vinculados.

Na listagem das Iniciativas deverá existir um checkbox:

☐ Definir público-alvo
☑ Criar material
☐ Publicar campanha

O checkbox representa o status da Iniciativa:

Desmarcado = pendente
Marcado = concluído 

O progresso da Ação deverá ser calculado automaticamente através das Iniciativas.

Regra:

Progresso = Iniciativas concluídas ÷ Total de Iniciativas × 100

Exemplo:

Uma Ação possui 4 Iniciativas:

☑ Iniciativa 1
☑ Iniciativa 2
☐ Iniciativa 3
☐ Iniciativa 4

Resultado:

2 / 4 = 50%

A barra deverá mostrar:

██████████░░░░░░░░░░ 50%

Outro exemplo:

5 Iniciativas, sendo 4 concluídas:

4 / 5 = 80%


15.1 Ação sem Iniciativas

Caso uma Ação ainda não possua nenhuma Iniciativa:

O progresso deverá ser 0%.
A barra deverá aparecer zerada.
O sistema não deverá apresentar erro de divisão por zero.

16. Ícone de usuários

Quando uma Ação possuir usuários vinculados, deverá aparecer um ícone de usuários ao lado do nome da Ação.

O mesmo comportamento deverá ser aplicado às Iniciativas.

Ao clicar no ícone, poderá ser exibida uma pequena janela/popover contendo os usuários vinculados.

17. Filtros da tela inicial

A tela Visão Geral de OKRs deverá possuir filtros.

Filtros obrigatórios:

Eixo

Permitir selecionar um Eixo específico.

Objetivo

Permitir selecionar um Objetivo específico.

Ação

Permitir selecionar uma Ação específica.

Meus itens

Adicionar um filtro:

Somente meus itens

Quando ativado, deverá mostrar somente os itens nos quais o usuário logado esteja vinculado.

Esse filtro deverá considerar principalmente:

Ações nas quais o usuário está vinculado.
Iniciativas nas quais o usuário está vinculado.

Também deverá manter a hierarquia necessária para contextualizar os resultados.

18. Comportamento dos filtros

Os filtros deverão funcionar de maneira combinada.

19. Troca de empresa

Quando o usuário trocar a empresa pelo seletor da barra superior:

Alterar a empresa ativa.
Atualizar o nome da empresa no menu superior.
Atualizar a cor da barra/área da empresa.
Recarregar os dados da tela.
Mostrar somente Eixos, Objetivos, Ações e Iniciativas daquela empresa.
Manter os filtros, caso ainda sejam válidos; caso contrário, limpá-los.

Exemplo:

Empresa atual:
[Cafaz Saúde ▼]

Usuário seleciona:

Cafaz Corretora

A aplicação deverá passar a trabalhar com:

empresa_id = Cafaz Corretora

Todos os novos OKRs cadastrados deverão ser associados à nova empresa.

22. Exclusões

As exclusões deverão respeitar a hierarquia.

Antes de excluir um registro que possua filhos, o sistema deverá solicitar confirmação e informar o impacto.

Exemplo:

Ao excluir um Eixo que possui Objetivos:

"Este Eixo possui 4 Objetivos, 12 Ações e 31 Iniciativas. Deseja realmente excluí-lo?"

Recomenda-se utilizar exclusão lógica (soft delete) para preservar histórico e evitar perda acidental de dados.

23. Experiência de uso

A interface deverá ser:

limpa;
moderna;
responsiva;
intuitiva;
orientada à visualização hierárquica dos OKRs.

A hierarquia deverá ser facilmente identificável visualmente.

Sugestão de interação:

▼ Eixo
   ▼ Objetivo
      ▼ Ação                 75%
         ├── ☑ Iniciativa
         ├── ☑ Iniciativa
         └── ☐ Iniciativa

Os níveis poderão ser expandidos/recolhidos para evitar uma tela excessivamente longa.

24. Estados vazios

O sistema deverá possuir estados vazios amigáveis.

Exemplo, quando uma empresa ainda não possui Eixos:

Nenhum Eixo cadastrado

Comece criando o primeiro Eixo para estruturar seus OKRs.

[ + Cadastrar Eixo ]

O mesmo princípio deverá ser aplicado a:

Objetivos
Ações
Iniciativas

Seleciona inicialmente Cafaz Saúde, caso o usuário tenha acesso a ela.

Redireciona para Início.

27. Modelo conceitual de dados

Estrutura sugerida:

users
├── id
├── name
├── email
├── password
└── permission

companies
├── id
├── name
├── cnpj
└── color

user_companies
├── user_id
└── company_id

axes
├── id
├── company_id
└── name

objectives
├── id
├── axis_id
└── name

actions
├── id
├── objective_id
└── name

action_users
├── action_id
└── user_id

initiatives
├── id
├── action_id
├── name
└── completed

initiative_users
├── initiative_id
└── user_id

O company_id dos níveis inferiores poderá ser obtido pela hierarquia, mas também pode ser armazenado diretamente caso seja necessário para performance e segurança. Se for armazenado, o backend deverá garantir que ele seja sempre consistente com a hierarquia.

28. Critérios de aceitação principais

A implementação deverá ser considerada correta quando:

 O login autenticar corretamente o usuário.
 O sistema identificar o nível de permissão.
 O Administrador tiver acesso completo.
 Gestor não conseguir acessar Usuários e Empresas.
 Colaborador não conseguir acessar Usuários e Empresas.
 O usuário só conseguir acessar empresas vinculadas a ele, quando aplicável.
 Cafaz Saúde for a empresa inicial quando o usuário possuir acesso a ela.
 A cor da empresa aparecer na barra superior.
 O usuário conseguir trocar de empresa.
 Eixos forem vinculados à empresa selecionada.
 Objetivos forem vinculados aos Eixos.
 Ações forem vinculadas aos Objetivos.
 Iniciativas forem vinculadas às Ações.
 Ações permitirem múltiplos usuários.
 Iniciativas permitirem múltiplos usuários.
 O ícone de usuários aparecer quando houver responsáveis.
 Iniciativas possuírem checkbox de conclusão.
 O progresso da Ação for calculado automaticamente.
 Os filtros funcionarem individualmente e combinados.
 "Somente meus itens" funcionar corretamente.
 Usuários não consigam acessar dados de empresas não autorizadas.
 A autorização seja validada no backend.
 A interface seja responsiva.
Todos consigam ver aquilo que estiver vinculado a empresa que o usuário estiver vinculado

Regra mais importante da aplicação

O contexto da empresa selecionada deve controlar toda a experiência de OKRs.

Em resumo:

Usuário → Empresas permitidas → Empresa selecionada → Eixos → Objetivos → Ações → Iniciativas

Usuários e Empresas são cadastros globais e constituem exceções a essa regra.
